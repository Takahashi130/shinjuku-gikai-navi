# 新宿区議会ナビ：区民参加機能の実装計画（2026-10-03 時点）

## あなたへの要約

- あなたが出した機能は全部この計画に入れました。入っているのは、議案の解説、解説へのコメント、賛成・反対の投票、議会とのズレの表示、5年間の評価、「議会と区民のどちらが正しかったか」、議員のページ、LIVE、区民だけの質問・いいねです。どこで作るかは下の対応表に書きました。
- 今回は計画を立てただけです。アプリとデータはまだ何も変えていません。
- 作る順番は次のとおりです。解説を読む → 投票する → 議会とのズレを見る → コメントする → 議員を知る → 数年後に答え合わせする → LIVE で参加する。
- 最初の目標は、10月15日に採決される議案のうち18件について、10月14日までに解説スライドを出すことです。
- 次に、賛成・反対の投票を10月12日ごろから受け付けます。締切は本会議の採決（10月15日14時）です。
- 区から採決の結果が出たら、「議会は可決、区民は反対が多い」といったズレと、会派ごとの賛否を並べて見せます。
- 投票、コメント、毎年の評価、LIVE 中の投票は同じしくみで作ります。区民かどうかを確かめられるようになったら、まとめて「区民だけ」に切り替えられます。
- 区のサイトから取り込むデータと、区民の票・解説は別の場所に保存します。区のデータを取り込み直しても、票や解説は消えません。
- 今の本番では「ログインなしで参加できるしくみ」が切られています。このままでは投票もコメントも動きません。Supabase の管理画面でスイッチを1つ入れてください。
- 解説は Claude が区の公開資料から下書きし、あなたが確認してから公開します。確認は1件10〜15分ほどです。
- 区民の確認は、将来の第三者による認証ができるまでは本格的にはできません。それまでの扱いは、すでにお聞きしている A/B/C で決まります。
- ほかに決めていただきたいことは「決めてほしいこと」に選択肢つきでまとめました。おすすめには（推奨）と付けています。
- 開発にかかる日数は、区民認証を除いて合計30〜40日ほど（Claude と一緒に作業する日数）の見込みです。
- LIVE 映像をこのアプリの画面に埋め込むことと、委員会での質問回数を数えることには、区や中継会社の許可が要ります。許可が出るまでは、別の方法（中継ページへのリンクなど）で始めます。

### 今日（10/3）新しく確かめた事実
- **`.github/workflows/deploy.yml` は毎回失敗しています**（`gh run list` で確認）。

- **`integration_test.yml` は CI で `supabase start` を使い、成功しています。**
  - ローカルで Docker を使わなくても、DB 関数（RPC）の統合テストは CI で回せます。

### 食い違いと統一の方針

| 論点 | 設計1 / 2 / 3 | 統一案 |

| 採決予定日 | 設計1：`vote_date date`。設計2：`final_vote_at` と `early_vote_at`（timestamptz） | **設計2の形にする。** 日付だけ必要なときは `final_vote_at` を JST の日付に変換して使う |
| 会派ごとの賛否のテーブル | 設計2と設計3で列も主キーも違う | 2.3 の形に1つにまとめる。`faction_id` は段階5で列を足す |

## 2. 共通の土台

### 2.1 データの持ち主（取り込みで上書きされない保存場所）

| 種類 | テーブル | 書き込むもの | 取り込み処理の扱い |
|---|---|---|---|
| 区のデータ（上書きしてよい） | bills, bill_contents, bills_tags, tags, diet_sessions（`final_vote_at`・`early_vote_at` を含む）, bill_faction_votes, members 関連, plenary_questions, faction_activity_expenses, council_meetings | `shinjuku-importer` | upsert、または消してから入れ直す |
| 運営者が作るデータ | bill_explainers, policy_metrics | 新しい `packages/navi-ops`（リポジトリの JSON から同期する） | **一切書かない** |
| 区民が作るデータ | polls, poll_responses, comments, comment_reports, comment_likes, resident_verifications | web の Server Action | `polls` に新しい行を追加すること（`ignoreDuplicates`）と、`closes_at_source='schedule'` の行の `closes_at` を更新することだけ許す |

- importer に、書き込んでよいテーブルの一覧（`IMPORTER_WRITABLE_TABLES`）を定数で置き、テストで守る。
- `bills.slug` の作り方は変えない。変えると bills の id が変わり、解説・票・コメントのひも付けが切れる。

### 2.2 匿名ログインと「参加者」

- **呼び出しの順番**
  1. ボタンを押す
  2. `ensureAnonymousUser()`（クライアント）
  3. Server Action
  4. `getSupabaseUser()` でログインを確認
  5. `resolveEligibility()`
  6. 回数制限と、ロボット確認（Turnstile）の検証
  7. 保存
- ページを開いただけでは匿名ログインしない（直前のコミットの方針どおり）。
- `voter_id` と `user_id` には auth.users の id を入れ、外部キーは張らない（report_reactions と同じ）。匿名ユーザーを消しても票は残る。
- 区民かどうか（`participant_eligibility`）は、**投票・投稿した時点の値をそのまま記録する**。A→B や区民認証に移っても、過去の票を作り直す必要はない。
- 誰が参加できるかは `polls.audience`（`anyone` / `resident_declared` / `resident_verified`）で回ごとに切り替える。区民だけにする切り替えは、この値を変えるだけで済む。
- Supabase Auth 側の CAPTCHA は使わない。admin のパスワードログインまで壊れるため、ロボット確認はアプリ側で検証する。

### 2.3 共通のテーブル設計

- どのテーブルも RLS を有効にし、ポリシーは作らない。読み書きは `createAdminClient()` から行う。
- 新しいテーブルは `tests/supabase/rls/default-deny.test.ts` の対象に足す。
- マイグレーションと `packages/supabase/types/supabase.types.ts` は同じコミットに入れる。

```sql
-- 共通：参加した時点の資格
create type participant_eligibility as enum
  ('unverified','self_declared_resident','self_declared_nonresident','verified_resident');

-- 投票・アンケートの「回」（議決への賛否・毎年の評価・LIVE中の投票を1つの形で）
create table polls (
  id uuid primary key default gen_random_uuid(),
  bill_id uuid references bills(id) on delete restrict,
  -- 段階7: meeting_id uuid references council_meetings(id) を追加し、
  --        check を ((bill_id is not null) <> (meeting_id is not null)) に替える
  kind text not null check (kind in ('decision','evaluation','live')),
  round smallint not null default 0,          -- decision=0, evaluation=1..5（可決からn年目）, live=連番
  response_type text not null check (response_type in ('choice','score')),
  options text[],                             -- choice の選択肢（decision は {for,against}）
  question text,                              -- evaluation・live の設問。decision は null
  audience text not null default 'anyone'
    check (audience in ('anyone','resident_declared','resident_verified')),
  opens_at timestamptz not null default now(),
  closes_at timestamptz,                      -- decision は採決の本会議の開始時刻
  closes_at_source text not null default 'schedule' check (closes_at_source in ('schedule','manual')),
  accepts_after_close boolean not null default true,
  is_hidden boolean not null default false,   -- 人事案件などを対象外にする
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (bill_id, kind, round),
  check (bill_id is not null)
);

create table poll_responses (
  id uuid primary key default gen_random_uuid(),
  poll_id uuid not null references polls(id) on delete restrict,
  user_id uuid not null,
  choice text,                                -- polls.options のどれか（アプリで確かめる）
  score smallint check (score between 1 and 5),
  eligibility participant_eligibility not null default 'unverified',
  resident_subject_hash text,                 -- 将来の区民認証で使う仮名ID。氏名・住所は持たない
  read_explainer boolean not null default false,
  responded_at timestamptz not null default now(),  -- 最後に選び直した時刻。採決前か後かの判定に使う
  created_at timestamptz not null default now(),
  unique (poll_id, user_id),
  check ((choice is not null) <> (score is not null))
);
create unique index on poll_responses (poll_id, resident_subject_hash) where resident_subject_hash is not null;
create index on poll_responses (poll_id, choice);

-- コメント（解説へのコメント。段階7bで LIVE の質問にも使う）
create table comments (
  id uuid primary key default gen_random_uuid(),
  bill_id uuid references bills(id) on delete restrict,   -- 段階7で meeting_id を追加
  kind text not null default 'comment' check (kind in ('comment','question')),
  section text not null default 'general'
    check (section in ('general','purpose','background','merits','concerns','correction')),
  body text not null check (char_length(body) between 2 and 400),
  user_id uuid not null,
  explainer_version int,
  eligibility participant_eligibility not null default 'unverified',
  status text not null default 'visible'
    check (status in ('visible','hidden_by_reports','hidden_by_admin','deleted_by_user')),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  check (bill_id is not null)
);
create index on comments (bill_id, created_at desc);
create index on comments (user_id, created_at desc);

create table comment_reports (
  comment_id uuid not null references comments(id) on delete cascade,
  user_id uuid not null,
  reason text not null check (reason in ('abuse','personal_info','spam','other')),
  created_at timestamptz not null default now(),
  primary key (comment_id, user_id)
);
-- 段階7b: comment_likes(comment_id, user_id, created_at, primary key(comment_id,user_id))
```

**運営者が作るデータと、区から取り込むデータ**
- `bill_explainers`：設計1の定義をそのまま使う。1議案1行で、`status`・`body`・`sources`・`reviewed_at`・`version`・`content_hash`・`publish_at`・`first_published_at` を持ち、「確認していないものは公開できない」制約を付ける。
- `diet_sessions`：`final_vote_at timestamptz` と `early_vote_at timestamptz` を足す。
- `bill_faction_votes`（区のデータ）：

```sql
create table bill_faction_votes (
  bill_id uuid not null references bills(id) on delete cascade,
  faction_abbr text not null,
  faction_name text not null,   -- その会期の凡例にある正式名（略称は年によって意味が変わる）
  vote text not null check (vote in ('for','against','unknown')),
  note text,                    -- 「1人反対」など
  sort_order smallint not null,
  updated_at timestamptz not null default now(),
  primary key (bill_id, faction_abbr)
);
-- 段階5で: alter table bill_faction_votes add column faction_id uuid references factions(id);
```

- **RPC は1つだけ**作る：`count_poll_responses_by_bill_ids(p_bill_ids uuid[], p_kind text default 'decision')`
  - 返す列は `(bill_id, choice, eligibility, cast_before_close, cnt)`。
  - `security invoker`、`set search_path = public`、`language sql stable` で作る（`count_reactions_by_report_ids` と同じ形）。
  - 統合テストは `tests/supabase/db-function/count-poll-responses-by-bill-ids.test.ts`（CI で実行）。

### 2.5 管理の仕方

`packages/navi-ops` を新しく作る。区のサイトを読む importer とは分け、運営の操作だけを置く。

| 対象 | 元になるもの | コマンド |
|---|---|---|
| 解説 | `explainers/<会期slug>/<議案slug>.json`（コミットする） | `explainers:check`（スキーマと、資料との照合）、`explainers:sync [--env prod]`（下書きはプレビュー URL を出す。最後に `/api/revalidate` を呼ぶ）、`explainers:status`、`explainers:publish <slug>`（`reviewed_at` を入れる。チャットでユーザーの承認を得てから実行） |
| 区の資料の材料 | `.materials/`（gitignore。DB にも入れない） | importer の `materials <会期URL>` |
| 投票の設定 | なし | `polls:set-close <slug> <日時>`（先議の議案など）、`polls:hide <slug>` |
| コメント | なし | `comments:reported`、`comments:hide <id>`、`comments:restore <id>` |
| 評価の数字 | `metrics/<議案slug>.json`（出典つき） | `metrics:sync`、`evaluations:open --year <n>` |

- 本番に書き込むとき（`--env prod` で `.env.supabase-prod` を読む）は、毎回ユーザーの確認を取る。
- 管理画面（admin）と admin MCP のツールは段階8に回す。それまではコマンドだけで運営する。
- 本番サーバーから AI の API は呼ばない。解説の下書きは、開発時に Claude が作る。

### 2.6 キャッシュ

- `web/src/lib/cache-tags.ts` に `BILL_EXPLAINERS`、`CITIZEN_VOTES`、`MEMBERS` を足す。
- 公開してよいかどうかと、締切を過ぎたかどうかは、キャッシュの外で `new Date()` と比べて決める（`hideUnpublishedStance` と同じやり方）。
- 票の集計は `unstable_cache` に60秒入れる。本人の票はキャッシュに入れず、楽観的更新で見せる。
- コメントはキャッシュしない。
- LIVE のコメントは Supabase Realtime を使わない（RLS で全部拒否しているため届かない）。15〜30秒ごとに読み直す。

## 5. リスクと対策

- **区のサイトの利用条件と著作権**
  - 区のサイトは無断の二次利用を禁止し、PDF への直接リンクを控えるよう求めている。
  - 解説は独自の文章で書き、資料からは短く引用して出典を付ける。
  - リンクは区の HTML ページに張り、PDF は資料名とページで示す。
  - PDF と抜き出した文字は、リポジトリにも DB にも保存しない。
  - 写真は複製も直接リンクもしない。
  - 既存の `bill_contents` は審議結果 PDF の文をそのまま載せているので同じ問題がある。区への確認を勧める。
- **会議録システムの robots.txt**
  - `ssp.kaigiroku.net` は自動取得を禁止している。許可が出るまで取り込みには使わない（調査で約10回呼んでしまっている）。
- **AI の下書きの誤りと偏り**
  - 項目ごとに根拠を必須にし、抜き出した文と数字を資料と機械で照らし合わせる。
  - 評価する言葉の禁止リストを使う。
  - 人が確認していないものは DB の制約で公開できなくする。
  - 「誤りの指摘」をコメントで受け、直したら版を上げる。
- **個人情報**
  - 政策への賛否は思想・信条に近い。生の IP は保存しない。
  - `user_id` は画面に出さず、議案ごとに変わる仮名で表示する。
  - 将来の区民認証では、氏名・住所を持たず、仮名 ID のハッシュだけを持つ。認証の前に同意をとる。
  - 議員の住所・電話・メールは保存しない。
  - 個人情報保護法の扱い（議員の情報をまとめて公開すること、会派＝信条に近いこと）は、専門家に確認することを勧める。
  - 参加の機能を出す前に、プライバシーポリシーを改定する。
- **なりすまし・ロボット・荒らし**
  - 匿名の ID は作り直せるので、1人1票は完全には守れない。
  - 対策を重ねる：ボタンを押したときだけサインイン、IP ごと・人ごとの回数制限、ロボット確認、1回ごとに1票の制約、違う人から3件報告されたら自動で非表示。
  - 携帯回線などで多くの人が同じ IP を使うため、IP の上限は緩めにする。
- **区の公式の住民投票との誤解、少ない票での断定**
  - 「非公式・参考値」と書き、区のロゴは使わない。
  - 最低票数と拮抗の幅を設け、採決前の票と後の票を分けて見せる。
- **選挙（公職選挙法。専門家への確認を推奨）**
  - 次の区議選は2027年4月ごろの見込み。
  - ランキングを出さず、全員を同じ形で見せる。
  - 選挙期間中は、会派と区民の一致率の順位を止める設定を用意する。
- **「どちらが正しかったか」の中立性**
  - 満足度は自分から答える人に偏る。利用者数と経済効果は区が出している数字。
  - 断定はせず、数字を並べ、計算方法を示す。否決された議案は事業がないので評価できないことも示す。
- **技術的なリスク**
  - 匿名ログインが無効のままだと、投票・コメント、既存の「参考になった」、AI インタビューがすべて失敗する。段階0で必ず有効にする。
  - deploy.yml の `config push` は Secrets を設定した瞬間に本番の認証設定を壊すので、段階0で外す。
  - マイグレーションは自動で反映されないので、開発用 → 確認 → 本番の手順を docs に固定する。
  - 区民のデータは `on delete restrict` にし、議案を削除しても票とコメントが消えないようにする。
  - slug の作り方は変えない。
  - 区のサイトの HTML や PDF の書式が変わったら、parser のテストと件数の確認で気づけるようにし、読めないときは手作業に切り替える。
  - 匿名ユーザーは自動では消えず、月間ユーザー数に数えられる可能性がある（未確認）。
  - 10/15 に間に合わないことがある。追加議案・臨時会・先議も前日までに解説を出せないことがあるので、その場合は「採決後に公開」と正直に表示する。
- **LIVE**
  - 埋め込みの許可が取れるまでは、リンクで済ませる。
  - 録画は約12日後に公開され、約1年で消えるので、期限のあるリンクとして扱う。
